Run by the builder on 2026-11-21 in a network-isolated box, on the release
tree at the commit this PR names (`package.json` 0.4.2, `main` at `2896d0c`
plus the stamp). What ships: `owned_keys:` on an application or service
(#177, PR #178). The maintainer's word on 2026-11-21: *"merged 178, cut the
cast release"*. As for 0.3.0, 0.4.0 and 0.4.1, what the box can drill is
drilled and what it cannot is waived, and this record says which is which.

### 2. The headline feature

**Through the shipped binary against a stub Coolify.**
`test/owned-keys-cli.test.ts` runs `dist/cli.js` of this tree against a
**stub** Coolify, with an admin whose `owned_keys` names `MCP_ENABLED` and
`RELEASE_TO`. Eight cases, all passing on this tree:

| leg | result |
|---|---|
| `apply`, existing application, owned and other keys drifted | the bulk env write carries the other keys and leaves out the owned ones |
| `apply`, an owned key absent live | written once, and only that one |
| `apply`, only owned keys differ | no write at all |
| `apply`, application absent | the create writes the owned keys from the template, and the plan says so |
| `diff --full`, only owned keys differ | `clean`; names them as `owned by the app — not compared`, never their values |
| `apply`, `{ file: }` pointing at a missing file | refused before any write |
| `apply`, existing service | the owned key stays out of the bulk write |
| `apply`, service absent | the owned key is written |

`test/owned.test.ts` (the resolver and its refusals) passes alongside:
37 tests across the two files.

## Waived

**The A→B promotion on two live Coolify instances** is **waived**, as it was
for 0.3.0, 0.4.0 and 0.4.1: the box reaches no Coolify, and cast still has no
drill harness of its own (#141, #142).

What this release therefore does not prove, stated so it is not rediscovered:

- that a live Coolify's bulk env endpoint leaves a key cast does not send
  untouched, so an owned key the app wrote survives an `apply`. The stub
  asserts what cast sends, not what Coolify keeps;
- that `diff` against a live admin reads back clean when only owned keys have
  moved.

The consumer's staging covers both: la-familia-site's `admin` declared with
`owned_keys: { file: .infra/admin-editable.json }` (#1086), a key changed in
the admin's «Configuración», then `cast apply` and `cast diff` showing it kept
and not compared.
