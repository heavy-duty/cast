tree at the commit this PR names (`package.json` 0.4.0, `main` at `2e926ef`
plus the stamp). What ships: `storages:` on a non-compose application (#167,

### 2. The consumer's shape through the shipped binary (the headline feature)

The shape heavy-duty/la-familia-site#273 will declare — the admin as a Docker
Image application with its store on a volume, no domain:

```yaml
admin:
  image: { name: ghcr.io/acme/admin, tag: stable }
  build: { pack: dockerimage }
  port: 8787
  healthcheck: /api/health
  storages:
    - { name: admin-data, mount_path: /data }
  domains: []
```

run through `dist/cli.js` of this tree against a **stub** Coolify
(`test/storages-cli.test.ts`, six cases, all passing on this tree):

## Waived

**The A→B promotion on two live Coolify instances** is **waived**, as it was
for 0.3.0: the box reaches no Coolify, and cast still has no drill harness of
its own (#141, #142).

What this release therefore does not prove, stated so it is not rediscovered:

- that Coolify 4.1.2 **accepts** the storage create and update bodies above.
  Every field is read off `ApplicationsController.php` at v4.1.2 (`storages`,
  `create_storage`, `update_storage`) and `ValidationPatterns.php`
  (`VOLUME_NAME_PATTERN`, `DIRECTORY_PATH_PATTERN`), not run against an
  instance;
- that a volume the API creates reads back as `<application uuid>-<name>`
  (read off `create_storage`'s `LocalPersistentVolume::create`);
- that the volume is mounted on the next deploy of a Docker Image resource.

The consumer's live criterion on #167 covers all three: the la-familia-site
admin created as a Docker Image resource with `admin-data` on `/data`, its
store restored onto it, and `cast diff` clean.
