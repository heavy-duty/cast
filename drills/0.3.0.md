Run by the builder on 2026-09-24 in a network-isolated box, on the release
tree at the commit this PR names (`package.json` 0.3.0, `main` at `64f0b4a`
plus the stamp). What ships: the `dockerimage` build pack and the enabled

## Waived

**The A→B promotion on two live Coolify instances** — `team`, `apply`, an
idempotent re-`diff`, `smoke`, `inventory`, `emit-draft`, `fleet --all`,
`destroy` behind its typed gate, the read-only guard — is **waived**, on the
maintainer's word above. The box this ran in reaches no Coolify, and cast
still has no drill harness of its own (#141, #142): the instrument is the
same gap 0.2.0 recorded.

What this release therefore does not prove, stated so it is not rediscovered:

- that Coolify 4.1.2 **accepts** the `POST /applications/dockerimage` body
  above and rolls the resource. Every field in it is read off the controller
  (`create_dockerimage_application`, `:896` and `:1792-1860`; the update
  allowlist `:2368`), not run against an instance;
- that `health_check_enabled: true` read back off a live 4.1.2 is a boolean or
  0/1 (both are handled); and that the empty compose domain stores as `null`
  on a live PATCH (read off the update route, `:2600-2606`, and Laravel's
  `ConvertEmptyStringsToNull`).

**Where the live half lands:** la-familia-site#264's staging migration is the
operator-owned verification named on cast#161 — the resource's deploy log
reading `Rolling update started` / `New container is healthy` / `Rolling
update completed`, and a 250 ms poll of `/` across a redeploy with no non-200.
If that migration finds this release's create body refused, the fix is a
0.3.1 and this record is the reason it was not caught first.
